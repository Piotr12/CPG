# MRP reruns: a rerun recalculates from scratch, nets accepted documents once, shows excess open supply without cancelling it, and never edits a document

**Status:** implemented. The service rerun tests live in `mrp-acceptance.service.test.ts`, the many-page R10 walk in `test-reset-realistic.test.ts`, and stored figures are read without the twelve-digit entry limit (Implementation notes).
**Created:** 2026-11-02 06:51 UTC
**Issue:** #288 (E19-S02, epic #271) · **Depends on:** proposal acceptance (`implemented/2026-11-01--0737UTC-mrp-proposal-acceptance.md`, #287), the MRP report (`implemented/2026-10-31--0907UTC-mrp-report.md`, #284), purchasing supply (`implemented/2026-10-31--0905UTC-mrp-purchasing-supply.md`, #276), production and transfer supply (`implemented/2026-10-31--0908UTC-mrp-production-and-transfer-supply.md`, #277), all merged · **Design authority:** `.ai/specs/product-brief.md` (R03, R05, R10, D04), `research/CPG-prd001.pdf` §04 "Reruns and duplicate avoidance", "Supply pipeline and overdue", `research/CPG-acceptance.md` RUN-008 … RUN-013, RUN-020

## 📝 TLDR

Planners rerun MRP whenever demand or stock changes, and since E19-S01 a run's proposals become real requisitions. Nothing yet proves a rerun is safe, and when demand falls the plan shows nothing about the supply that is no longer needed.

After this change (future behaviour):

- Each plan reports **`excess`**: the open supply its documents bring that the horizon doesn't need. It is the amount by which the last day's balance before proposals exceeds that day's safety target, capped at the open supply the plan counts. The API's latest-run read lists it, and the opened plan on the MRP page states it. Nothing is cancelled, reduced or rescheduled (R10).
- A test suite proves the rerun contract that the engine and run service already follow. A rerun plans from a fresh snapshot under a new run ID. Accepted documents keep their run tag and count as supply once. A cancelled requisition doesn't count. When demand grows, only the uncovered rest is proposed. A rerun over unchanged data gives the same proposals. No document's fields, version or audit history change.

## 📝 Problem Statement

- **The rerun contract is unproven.** RUN-008 … RUN-013 and RUN-020 are "Not executed" in the acceptance catalogue. The code already behaves as required:
  - `planMrp` (`domain/mrp/plan-mrp.ts`) is a pure function of `MrpSnapshotService.load(today)`, so a rerun never remembers an earlier run;
  - an Open requisition is tentative supply (`supply/purchasing-supply.ts`, whatever its `mrpRun`), and a cancelled one is skipped by `status !== "open"`;
  - `MrpRunService.run` deletes the previous run's daily results, proposals and exceptions, and writes only its own four tables and one `mrp.mrp-run.created` audit entry;
  - `MrpAcceptanceService.accept` refuses a superseded run's proposal as `MRP_PROPOSAL_STALE`.

  No test ties these together across two runs, and none proves R10 over every page of each document list.
- **Excess is invisible.** When demand falls below what open documents bring (RUN-010: an Open production order of 100, demand 80), the plan's balance simply ends at 20. Nothing tells the planner that 20 of planned supply is unneeded. Since R10 forbids MRP from cancelling or rescheduling, showing it is the planner's only signal (PRD §04: "surplus planned supply visible").

## 📝 Proposed Solution

1. **`planExcess`**, a pure function of a plan's days (bigint micro-units, R03):

   ```ts
   type ExcessDay = Pick<MrpBucket, "tentativeSupply" | "dependableSupply" | "transferIn" | "safetyTarget" | "projectedBefore">;
   function planExcess(days: readonly [ExcessDay, ...ExcessDay[]]): bigint
   ```

   It sums the open supply, takes the last day's surplus over its target, and returns the smaller of the two, never below zero.
2. **`summarizePlan`** reads the four extra figures from the stored days (`parseSignedQuantity`), calls `planExcess` and returns `excess` as a fixed six-decimal text (`formatDecimal(…, { fixed: true })`; the value is never negative). `MrpPlanSummary`, and so `MrpPlanView`, gain `excess: string`. The weekly view doesn't need it.
3. **Screen and help**: one sentence in `PlanDays` when `excess` is above zero (EN/PL), and one sentence in the `mrp` help topic.
4. **Tests that prove the rerun contract**: engine tests (`plan-mrp.test.ts`, the same fixture planned before and after "acceptance", a document added to the snapshot), run-service tests, and `tests/integration/mrp-rerun.test.ts`.

**Alternatives considered.**

- *Store excess in `mrp_daily_result` or `mrp_run_exception`.* That needs a migration or a new code, and old runs would read zero. The figure is fully derivable from stored days, as `lowestProjectedBefore` already is.
- *Measure excess on `projectedAfter`.* Lot rounding would then count as excess: AC2's 25 for a need of 20 would show 5.
- *Excess per document* (which order is unneeded). That needs an allocation rule (latest due first?) that the PRD doesn't give. The pair total answers RUN-010, and the plan already lists its documents. Deferred to E18 if wanted.
- *An "excess" exception or warning.* It is neither: nothing is wrong with the plan, and a warning is defined as overdue supply (E18-S02).

## 📝 Data Model

No change. Excess is derived on read from the stored `mrp_daily_result` figures.

## 📝 API Contracts

`GET /api/tenants/{tenant}/mrp/runs/latest`. **Additive:** each plan adds `excess`, a six-decimal string in the material's base unit, zero or more, `0.000000` when there is none. Definition: the smaller of (the last day's `projectedBefore` less its `safetyTarget`, floored at zero) and the plan's open supply over the horizon (the sum of `tentativeSupply`, `dependableSupply` and `transferIn` over its 90 days). It counts no proposed receipt and no at-risk supply. A Make proposal's component needs are part of its components' `dependentDemand`, so a component's excess already leaves out what a parent proposal needs. Filters, paging, `run`/`generation` and every other field are unchanged. It holds for runs stored before this release too. `BACKWARD_COMPATIBILITY.md` gets an "Additive since E19-S02" bullet under the MRP routes.

No other route changes. `POST …/mrp/runs` and `POST …/proposals/{id}/accept` keep their behaviour, which this story only proves.

## 📝 Edge Cases & Failure Scenarios

- **Late supply and an early shortage.** A requisition of 100 due on day 40, with demand of 80 on day 5: day 5 runs short and gets a proposal, and the last day's balance before proposals is 20, so excess is 20. Both are true: the document comes too late for the need it might have covered, and 20 of it is unneeded. MRP reschedules nothing (R10).
- **Physical surplus only.** Stock of 200, no open documents, demand of 80: excess is 0 (the cap). Physical stock isn't planned supply.
- **Safety stock.** Target 10 on the last day, balance 30, supply 100: excess is 20.
- **An accepted lot-rounded proposal.** Run 1 proposes 25 for a need of 20 and shows excess 0. Once the proposal is accepted, run 2 has an Open requisition of 25, no proposal, and excess 5 (Q1). This is pinned by a test.
- **A component of a Make proposal**: the proposal's need is the component's dependent demand, so component supply that a parent proposal uses is never excess.
- **Supply beyond the horizon** counts on no day (#277's rule), so it is neither supply nor excess.
- **A transfer's source** sees the dispatch as demand and its destination the receipt as supply, so excess at the destination counts the transfer once.
- **Unreadable material** (Invalid UoM Conversion): its stored figures are the incomplete ones the plan has, as for `lowestProjectedBefore`. Excess follows them and needs no special case.
- **A run stored by the previous image during a deploy**: the read derives excess from its stored figures, so it shows correctly. During the overlap, a previous image answers without the field. The field is additive.
- **Determinism**: the same snapshot gives the same proposals in the same order (`plan-mrp.ts` sorts on content). Only `id` differs between runs (Q8).

## 📝 Risks & Impact Review

- **Contract**: one additive read field. No stored data, so a revert removes it cleanly.
- **Semantics**: excess describes the current documents, so it can appear on a rerun right after an accepted lot-rounded proposal, with nothing else changed (Q1). That is accurate (the document does exceed the need), and the screen gives no advice to cut. If the owner prefers excess net of lot rounding, that is a later change to this one function. Excess is a pair total, not an allocation to documents. If E18 later wants per-document excess, that is a new field, not a change to this one.
- **Test cost**: the integration file creates over 100 documents of each list (Q9). Create them through the API in a loop with the file's own materials. Measure the file's run time against the suite's shard budget, about 7 min per shard (AGENTS.md), and reuse the existing `allPages` helper.
- **Product direction call, not a defect**: whether excess should count tentative supply (requisitions). This spec counts it, because an unneeded Open requisition is exactly what a planner should cancel by hand (RUN-012's netting already treats it as supply).

## 📝 Decisions in play

- R03: excess is exact six-decimal BUoM arithmetic on bigint micro-units.
- R05: every test runs in one tenant; nothing crosses Test and Prod.
- R10: MRP runs only on demand and never rewrites an existing document. This story's tests are its proof, and excess is shown, never acted on.
- D04 (owner: Piotr12): the simplest consistent excess definition (Q1). No per-document allocation and no new column.
