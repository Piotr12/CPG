## Goal

In each tenant the admin defines logical BOMs: an eight-digit ID, one intermediate or finished output, an active flag, and a recipe with a priority, inclusive validity dates and raw or intermediate components per one output base unit. Components are stored exactly in their base units, with the entered unit and factor kept. A real change creates an immutable revision. An identical save or a toggle creates none. Equal priority over overlapping validity and cycles are refused, and BOM references lock a material's type and base unit. This works on two screens and through the API, every signed-in user reads BOMs, every change is audited, and Test is seeded with three demo BOMs.

## Deviations from the spec

- **Field errors are keyed by their full path** (`core/src/http/parse-input.ts`): `z.flattenError` keyed a list item's error by the list's name only (`components`), so a line's error couldn't reach its row. A top-level field keeps its plain name, so every existing form and route is unchanged.
- **The details of `BOM_CYCLE` and `BOM_PRIORITY_CONFLICT` come after the first colon of the message, language-neutral** (`→(BOM 00000007)` per step; `BOM 00000001 (2027-03-01 – …)`), so a screen appends them to the sentence it translates. A new BOM's own step is a bare `→`, since it has no ID until the checks pass.

- **`BASE_UNIT_IN_USE` and `MATERIAL_TYPE_IN_USE` are translated generically on the screens** (the API's English message names the BOM): the materials screens translate by code, and the base-unit text now covers both BOMs and planning rows.
- **The recipe form's controls carry `name` attributes** (`components.0.material`, …), matching the field-error keys, so browser tests and the error mapping use one naming.
- **No acceptance-catalogue statuses changed here**: as for E02 and E03, the epic's closing PR updates them.
